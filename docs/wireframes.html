Process flow

Seven steps from an uploaded CSV to an exported approved list. The spine is the happy path; boxes to the left are refusals that write nothing, boxes to the right are the records the flow reads and writes. Step 5 loops once per approval level.

BMD user action Platform / Apex Approver action Record store / read source Refused — nothing written
  • Status lives on the invitee, not the event. The event carries three roll-up counts — Pending, Approved, Rejected — so one AM's pending batch never blocks another's.
  • The chain is stamped whole, not walked. All five approver fields plus Approval_Levels__c are resolved at submit and frozen, so a reorganisation mid-approval cannot reroute an item somebody is already looking at.
  • The approval process itself is five pre-provisioned steps, each addressed to its own Approver_N__c and gated on NOT(ISBLANK(Approver_N__c)). A two-level chain simply skips steps 3–5; steps 4 and 5 are labelled Reserved because the shipped configuration never fills them.

Approval chain

Who signs is resolved once, at submit, from the org chart: level 1 is the Account Owner snapshotted onto the invitee, and each level above is that person's manager, up to the level cap or the first Regional Head — whichever comes first. Two invitees on the same event routinely have different chain lengths, which is why the approver's screen says Level 2 of 3 rather than assuming.

No chain, so the whole batch is refused — with a named error, nothing written, and the rows left in Draft. The remedy is data: an account kept for non-customer guests, whose owner becomes their level 1.

  • Four ways a submit is refused, all of them whole-batch. No Account Owner on some row; an inactive user anywhere in the chain; a manager the submitter cannot see; and a chain whose only member is the submitter. Each raises ApprovalChainService.UnroutableException before any DML, and each message names the cause and the remedy and ends “Nothing was submitted.”
  • A chain the running user cannot read in full is refused, not truncated. Under a restrictive User sharing model the walk can lose sight of a manager; approving with fewer signatures than the business asked for, silently, is the outcome that rule exists to prevent.
  • The cap and the title markers are one Custom Metadata record, Approval_Chain_Setting__mdt.Default — shipped as Regional Head and 2. Raising the cap to 3 or 4 starts populating Approver_4__c and Approver_5__c with no deploy; anything above 5 is clamped, because a level no approval step can address would strand the invitee.
  • Title matching is a case-insensitive substring against a comma-separated list, because real titles carry a region. That also matches “Assistant to the Regional Head”, which is why the marker is a setting an admin can narrow rather than a string in the code. A blank list is legal and means no early termination.
  • Unverified from this repo: whether this org populates User.Title at all. An unmatched title does not error — every chain simply climbs to the cap, so the symptom is approvals taking one signature longer than expected.
  • What it costs: the chain can no longer be edited as data. Changing who signs means changing the org chart, which is an administrator's Setup change rather than a row an operations team can add.

Upload a CSV (.csv) file — comma, semicolon or tab separated. Everyone in it becomes an Event Attendee, ready to be invited to any event. Expected headers: First Name, Last Name, Email, Company (Title and Mobile optional).

Nothing else in the org is touched: no contact, lead or account is created, changed or read. People already imported are recognised by name, company and email, so re-uploading a file updates them instead of duplicating them.

Save it as UTF-8 (in Excel: File → Save As → “CSV UTF-8”), otherwise accented names cannot be read.

  • The result is a heading and two paragraphs, not a success banner. The count of created and refreshed rows is the news; the no-contacts-were-touched sentence is repeated here because it is the promise the whole import is judged on.
  • “Import Another File” resets everything, including the skipped list — which is why the copy says so before the user presses it.
  • Skipped and Failed are two different downloads, because they are two different facts. Skipped rows were refused by the preview and never written; failed rows were attempted and refused by the database — a surname that is purely a number, say, which a validation rule rejects whoever writes it. Each carries its own reason column, and both are formula-guarded on the way out.
  • A partial import is reported as a partial import. Within a batch the upsert is allOrNone = false, so one bad row cannot take the other 199 down; between batches nothing can be rolled back, so if a whole call throws the error says which batch it was and how many had already been applied.
  • The parse is entirely client-side: delimiter sniffed from the header line, UTF-8 decoded with fatal: true, BOM stripped, rows de-duplicated on the same key the server upserts with. One file may carry 8,000 rows, and de-duplication happens across the whole file before it is chunked — so no person can land in two batches.
  • Both Apex calls are chunked at 200 rows and run one after another, not in parallel: previewMatches while checking, applyChanges while importing. The spinner carries “Checking batch 3 of 40…” so a long import does not look hung, and the label stays blank when there is only one batch. The server's own guard is 1,000 rows per call, so the client's 200 can be re-tuned without a redeploy.

Screen 2 · Create Marketing Event

The standard create modal driven by the page layout — no custom code. Status is deliberately absent: it belongs to the invitee, not the event. Topic is absent too: it is a free-text child object a BD adds after the event exists, not a field on this form.

New Marketing Event Standard record form

New Marketing Event

Information

  • The layout is two columns, top to bottom: Name, Event Date, Location, Event Type on the left; Expected Attendees, Description, Owner on the right. The modal interleaves them, which is what a two-column layout looks like in a create dialog.
  • No Status field. Several AMs submit independent batches, so an event-level state machine would deadlock. The event carries roll-up counts instead — and they sit in a separate read-only Review Progress section that a create form does not show.
  • Topic became Event_Topic__c, one free-text row per tag. It replaced a restricted multi-select whose value set an admin had to seed in Setup before anyone could tag anything; a BD now types the tag themselves, and the permission sets follow — BD gets create/read/edit/delete, an approver gets read. The cost is the one Company__c already pays: “AI & Data” and “ai and data” are two tags, and nothing rolls them up.
  • Where a BD actually types that tag is worth checking in a real org. The page layout carries an Event Topics related list, but the Lightning record page (Screen 3) is a FlexiPage with no related-list component in any of its four regions — highlights, the two custom LWCs and the detail panel. As shipped, that leaves the related list nowhere to appear.
  • Save navigates straight to the record page, which is where Screen 3 lives.

  • The group header carries the selection, not the size. It reads “Nordbank AG — 2/14 selected”, recomputed as ticks change, and falls back to “(no company)” when the imported text was blank. Grouping is by company text, because an attendee has no Account behind them — two spellings of one organisation group separately, and the screen does not pretend otherwise.

  • The chain sentence in the toast appears only when a chain is longer than one level — on the common case it would be noise, and on the uncommon one it is the whole news.

  • The rows are work items, not invitees. Company, title and remark live on the target record, so this list cannot show or sort by them at all — the reason Screen 4b was built.
  • Five steps, one of which is yours. Each step is gated on its own Approver_N__c being populated, so a two-level chain runs steps 1 and 2 and skips the rest. Steps 4 and 5 are labelled Reserved: they exist so the cap can be raised in configuration without a deploy.

  • A rejection at any level ends the whole request; no level above is asked.
  • The AM hears once, at the end. Invitee_Decision_Completion fires when a submitter has nothing left pending on the event: “… fully reviewed: X approved, Y rejected”, pointing at the Approved Invitees reports.

  • Nothing starts selected. Pre-ticking every row would make “approve everybody” the path of least resistance, which inverts what an approval is for.
  • The group buttons act on the group's selection, not on the group. They read Approve 3 when three of that company are ticked and fall back to a disabled Approve when none are — so the company tick and the decision stay two deliberate steps, and a stray tap on the header cannot decide anything.
  • The company checkbox goes indeterminate when only part of a company is selected, set from renderedCallback because indeterminate is a DOM property a template cannot express.
  • The table has no visible header row. Its thead is slds-assistive-text: four columns of headings above two-line name cells would cost more than they explain, and a screen reader still gets them.
  • “Level 1 of 3” is deliberately quieter than VIP. VIP is a claim about the guest and should catch the eye; the level is context about the decision — whether this signature is the last one — and must not compete for attention on every row. It is hidden entirely on a one-level chain.
  • Two invitees on one event legitimately show different chain lengths, because a Regional Head ends a chain wherever they appear. Nordbank's owner is three rungs below one; Helvetia's reports to one directly.
  • The customer code is the Account's AccountNumber, and when it is blank the line says No customer code rather than going empty. A guest with no Account at all gets an italic Not a customer instead — a branch that survives from R8 and can no longer hold pending rows, since routing starts at the Account Owner and such a guest is refused at submit.
  • Grouping is by Account where there is one, and by the snapshotted company text otherwise — deliberately not one bucket for every unlinked guest, which would put unrelated people behind the same button.
  • “Waiting on me” is read from ProcessInstanceWorkitem, not from a field comparison. Approver_2__c is populated from the moment of submission, so a field test would let a level-2 approver act on work that level 1 has not released yet.
  • Remark and VIP sit on the row, because they are the AM's case for inviting this person, and the approver is the reader they were written for. The name carries the snapshotted salutation when there is one.
  • Capped at 200 invitees per decision: refusing at a stated number beats a governor limit surfacing as an unexplained error. Rows that stopped being yours between load and click are reported back as skipped rather than silently dropped.

  • One report covers both entry points. To get one event, filter it; to get all of them, don't. It is a Summary report grouped by event name with subtotals, so the group rows are the per-event counts — and the export is Export → Details Only, choosing CSV or XLSX and the encoding.

  • Approver became Approver 1, and Approval Levels joined it. Approvers 2–5, Current Level, Submitted At, Attended and Status are in the report type but unchecked — a fully approved row's interesting number is how many people had to agree, not which of five fields held them.

  • Known gap: the standard exporter does not guard against CSV formula injection. Only Screen 1's Download Skipped Rows still does.
